# Admin workflow dashboard design

## Goal and scope

Replace the summary-only admin screen with usable workflows for the existing user, traveler, destination, travel, payment-gateway, and payment-method endpoints. Work on the current `build-security-data-fixes` checkout. Preserve the current visual palette and mobile layout. The UI must show provider status/failure and the current backend's synchronous or pending responses without claiming that sandbox tokenization happens in the browser.

## Components and data flow

- A shared API client adds the bearer token, parses safe error codes, handles `401` by ending the local session, and reports `403`/`503` plainly. Login stores the access token and expiry in session storage; logout calls the auth endpoint and clears local state even if that request fails.
- Three main sections use focused components: users/travelers, destinations/travels, and gateways/methods. Each section loads its own data when selected and refreshes after mutations. Collection pages expose previous/next controls where the backend returns a page.
- Forms keep their values on failed requests, disable only their own submit controls while requests run, show validation and dependency errors beside the workflow, and ask for confirmation before destructive actions.
- Travel editing sends the existing backend's complete aggregate shape: ordered destination stops, activities, accommodation, and transport. Traveler participation uses the existing trip/traveler routes. Shared destinations are managed separately.
- Payment method creation accepts only a provider reference generated by a Stripe or PayPal sandbox flow outside this UI, plus local user, gateway, and display label. The UI generates and retains an idempotency key across retries. It never asks for card numbers or security codes. It shows `PENDING`, `ACTIVE`, `FAILED`, and `DELETION_PENDING` states and safe failure codes.

## Limits and verification

The current backend has no provider tokenization handoff screen, provider-customer ownership binding, default-method operation, or asynchronous operation resource. Do not invent those controls. The backend's user-creation flow does not return initial credentials; the UI must not imply that an account is immediately usable without the operator credential process. Compile the production UI and inspect its output; do not add or run tests under the current task instruction.
