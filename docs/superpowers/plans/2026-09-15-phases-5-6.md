# User and Travel Management Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Deliver administrator CRUD for users/travelers and complete in-memory travel and itinerary management APIs matching the published contracts.

**Architecture:** Each service owns validated domain records behind a repository/service boundary. Controllers expose paginated REST resources and map validation, missing resources, conflicts, and malformed UUIDs to stable HTTP responses. Storage is intentionally isolated so Phase 2 database adapters can replace the in-memory repositories without changing API behavior.

**Tech Stack:** Java 21, Spring Boot 4.1.1 WebMVC, Spring Security, Jakarta Validation, JUnit 5.

**Spec:** `plan.md`, `docs/api/users.yaml`, `docs/api/travels.yaml`.

## Global Constraints

- Business APIs require `ADMIN` authentication at gateway and service boundaries.
- IDs are UUIDs; list results are deterministic and paginated.
- Dates use ISO-8601 local dates and duration includes both endpoints.
- No sensitive credentials or payment data are stored in these services.

### Task 1: User and traveler domain

Create records, repository, validation, and CRUD service with duplicate-email and ownership checks.

### Task 2: User and traveler REST API

Expose list/detail/create/update/delete endpoints with stable errors, pagination, and idempotency-key replay.

### Task 3: Travel graph domain

Create travel, destination, stop, activity, accommodation, transport, and participant records with date and itinerary validation.

### Task 4: Travel REST API and tests

Expose destination/travel CRUD, participant operations, deterministic pagination, and deletion rules; add unit tests and update tracking.
